# R1.1 — 仓库骨架与工程约定

> 任务：`docs/rewrite-plan-r1-r5.md` §4.2（R1.1a–R1.1e）。
> 目标技术栈：TypeScript / Web（§1.2 已定）。

---

## 1. 目录结构（R1.1a）

```text
nc-reactor-generator-chinese/          ← Java 冻结基线原样保留（tools/ 是基线再生器）
├── package.json                        pnpm workspace 根
├── pnpm-workspace.yaml                 packages/*；allowBuilds: esbuild
├── tsconfig.base.json                  路径别名 @ncplanner/*
├── tsconfig.json                       tsc --noEmit 覆盖 packages/** 与 tools/ts/**
├── vitest.config.ts                    别名 + 测试收集规则
├── packages/
│   ├── ncpf/        # 格式与数据模型（无 UI、无 IO 以外的依赖）
│   ├── kernel/      # 物理内核（唯一实现；禁止 import UI）
│   ├── formats/     # reader / writer（R1.4）
│   ├── i18n/        # LocaleManager / MessageBundle / DataNameBundle（R1.2）
│   └── app/         # UI —— R1 只有占位说明，R3 才实现
├── lang/            # en_US（规范源）+ zh_CN 语言包
├── datasets/        # R0/R1 产物（黄金数据集 / fixtures / 元素清单 / BASELINE.md）
├── tools/
│   ├── golden/      # R0 Java 基线再生器（保留，见 §11.4）
│   └── ts/          # lint / port-audit / 迁移脚本 / 调试工具
└── docs/r0, docs/r1 # 发现、决策、验收记录
```

约定：

- ESM（`"type": "module"`），包内相对导入带 `.js` 后缀（TS `moduleResolution: Bundler` + Vite 解析）；
- 跨包导入只用别名 `@ncplanner/*`，由 `tsconfig.base.json` 与 `vitest.config.ts` 同步维护；
- 测试位于 `packages/<pkg>/test/**/*.test.ts`；
- **零运行时依赖**：`ncpf`/`kernel`/`formats`/`i18n` 目前都不依赖任何 npm 包（i18n 的 ICU 子集是手写的）。

## 2. 依赖方向强制（R1.1b）

- 允许：`app → formats|i18n|kernel → ncpf`；
- 禁止：`kernel`/`ncpf` 导入 `@ncplanner/app`、`@ncplanner/i18n` 或任何 UI 框架。

由 `tools/ts/lint.mjs` 作为**硬错误**检查（`pnpm lint`，也在 CI 里跑）：
不需要 ESLint 依赖即可完成结构性检查，避免 R1 引入构建期负担。
（计划里写的是 `no-restricted-imports`；这里是等价实现，理由与差异记录在本文件。）

## 3. 测试与覆盖（R1.1c）

- Vitest；`pnpm test` 默认跑抽样（前 120 例），`NCPL_GOLDEN=full` 跑全量 5,000+5,000；
- `datasets/` 与 `datasets/configurations/*.ncpf.json` 通过**相对路径**接入（不复制），
  这样「数据集就是验收标准」这件事在仓库里是可见的；
- 当前规模：`packages/ncpf` 12 项、`packages/kernel`（黄金 SFR/USFR + 手算 + 重建）、
  `packages/i18n` 58 项；`pnpm typecheck` 干净。

## 4. 「禁止裸字符串」（R1.1d）

`tools/ts/lint.mjs` 的第二个规则：扫描 `packages/{ncpf,kernel}/**` 的字符串字面量，
把「像散文」的字面量（≥2 个词、含大写开头词或两个小写词，且不是
模块名/身份键/路径）列为 burn-down 项，基线在 `tools/ts/bare-strings-baseline.json`。

- 开发者可见文本（`throw new Error(...)`、`console.*`）按构造豁免 —— 它们不是 UI 文案；
- 新增散文会**直接失败**，必须显式写进基线（并标注 `TODO(R3.8)`）；
- 现状：核心包 0 条裸散文（物理内核里本来就没有用户可见文案，R3 的 UI 才需要走 ICU key）。

## 5. 文档纳入仓库（R1.1e）

`docs/r0/**`（R0 发现/契约/覆盖表/往返）与 `docs/r1/**`（R1 决策与验收）都在仓库内，
可追溯路径：`发现 → 决策 → 数据基线 → 验收结果`：

```text
docs/r0/findings.md        发现
docs/r1/d1-decision.md     决策（含未修项与理由）
datasets/golden/BASELINE.md 数据基线
docs/r1/r1.5-kernel.md     验收结果
docs/r1/port-audit-file-level.md 移植量复核 → 排期修正
```

## 6. CI（R1.1 附）

`.github/workflows/ci.yml`：install → typecheck → lint → 全量测试（含黄金数据集）
→ port-audit 确定性检查。**不需要 Java、不需要 GL**：数据集与配置都在仓库里，
这正是 R1 可以把「物理正确性」放进 CI 的前提。

## 7. 与计划的差异

| 计划 | 实际 | 理由 |
|---|---|---|
| ESLint `no-restricted-imports` | `tools/ts/lint.mjs`（无依赖） | R1 目标是内核正确性；零依赖脚本已能覆盖结构性规则，且 CI 更快。若 R3 引入 UI 框架，再换 ESLint 并把规则逐条搬过去 |
| `pnpm build` 通过 | `pnpm typecheck` 通过（无 bundle 步骤） | R1 没有可发布的产物；`build` 在 R3 引入 app 时才有意义 |
