# R1.0e — 黄金数据集 v3：为什么必须换掉模板命名

> 任务：`docs/rewrite-plan-r1-r5.md` §4.1 R1.0e（D1 决策落地）与 §3.1.6（数据集版本）。
> 结论：**数据集升到 `datasetVersion 3`**，模板名与配方名从
> `NCPFElement.getName()` 换成 `NCPFElementDefinition.toString()`。
> 物理值不变（逐条验证 0 差异），但**可重建性**从「有歧义」变成「无歧义」。

---

## 1. 问题：`getName()` 不是单射

R0 的数据集用 `NCPFElement.getName()` 记录方块：

```java
private static String templateName(Object block){
    Object t = field(block, "template");
    if(t instanceof NCPFElement)return ((NCPFElement)t).getName();   // ← 有损
    ...
}
```

而 `NCPFElement.getName()` 返回 `definition.getName()`，
对 `legacy_block` 只返回 `name`，**丢掉 metadata 与 blockstate**。

实测这会在 SFR 配置里把下列互不相同的方块压成同一个名字：

| 名字 | 实际变体数 | 物理差异 |
|---|---:|---|
| `nuclearcraft:solid_fission_sink` | 16 | 冷却值不同（水 55 / 铁 50 / 红石 85 …） |
| `nuclearcraft:solid_fission_sink2` | 16 | 同上 |
| `nuclearcraft:fission_reflector` | 2 | **反射率 1 vs 0.5、效率 0.5 vs 0.25** |
| `nuclearcraft:fission_shield` | 2 | 开/闭（闭环是没有 shield 模块的普通方块） |
| `nuclearcraft:fission_vent` | 2 | 输入/输出（只影响提示，不影响数值） |
| `nuclearcraft:fission_cell_port` / `fission_irradiator_port` | 各 2 | 输入/输出 |

用 v2 数据集重建时，TS 只能「按名字取第一个变体」，因此
**在 600 例抽样里就已经有 3 例（`mixed` 策略）无法复现**；
按 5000 例推算约 20–25 例，且全部集中在含散热器/反射器的布局上。

> 这不是 TS 的问题，是数据集本身丢信息。R0 的 `port-audit` 与 `golden-datasets`
> 都把它记为「数据集的自描述性」风险。

## 2. 修法（`tools/golden/src/.../GoldenGen.java`）

```java
return ((NCPFElement)t).definition.toString();   // legacy_block → name:meta[blockstate]
return ((NCPFElement)v).definition.toString();   // 配方同理
```

`NCPFElementDefinition.toString()` 对 `legacy_block` 输出
`name[:metadata][blockstate]`（blockstate 的 key 已排序，见
`NCPFSettingsElement.stringifyBlockstate`），对 `oredict` 输出 oredict 串，
对 `legacy_recipe` 输出 `[in*1, …]->[out*1, …]`。
它与 TS 侧 `packages/ncpf/src/element.ts` 的 `definitionIdentity()` 逐字符一致。

meta 同时新增两个自描述字段：

```json
"templateNaming": "NCPFElementDefinition.toString() (injective)",
"recipeNaming":   "NCPFElementDefinition.toString() (injective)"
```

## 3. 验证：命名改动是物理中性的

同一 seed（20260101）+ 同一参数重新生成 5000 例，与 v2 逐条对比：

```text
checked 5000 · editor diffs 0 · error diffs 0      (Overhaul SFR)
checked 5000 · editor diffs 0 · error diffs 0      (Underhaul SFR)
```

即 15 个数值字段（含 `error` 标记）**逐条完全相同**，只有 `blockNames` / `recipeNames`
变得更精确。旧文件保留为 `datasets/golden/*-cases.v2.jsonl.gz` 供对照。

## 4. 对 TS 侧的影响

- `rebuildSfr` / `rebuildUsfr` 先用 `definition.identity` 查表；
- 查不到时**退化为按 `definition.name` 取第一个变体，并把该歧义记录在
  `RebuildResult.ambiguous`**（测试会打印出来）。v3 数据集下该集合为空，
  这条退化路径因此同时充当「数据集是否又退化成有损命名」的回归哨兵；
- 配方名解析（`fuel=` / `irradiatorRecipe=` / `recipe=`）同样匹配
  `definition.toString()`（含 `*amount`，见 `stackToString`）。
  这条一开始写错（漏了 `*1`），导致 170 个辐照器方块收不到配方、
  进而少算了慢化剂连线 —— 属于「静默失败」，现已改为**查不到即抛错**。

## 5. 复现

```powershell
# 已编译好的 harness（app classes 在 tools/golden/build/classes）
pwsh -File tools/golden/golden.ps1 -Type sfr          -Cases 5000 -Seed 20260101 -MinSize 3 -MaxSize 14 -Out datasets/golden/sfr-cases.v3.jsonl  -SkipCompile
pwsh -File tools/golden/golden.ps1 -Type underhaul-sfr -Cases 5000 -Seed 20260101 -MinSize 3 -MaxSize 14 -Out datasets/golden/usfr-cases.v3.jsonl -SkipCompile

# 压缩（仓库只保留 .gz）
node -e "const z=require('zlib'),f=require('fs');for(const n of ['sfr','usfr'])f.writeFileSync('datasets/golden/'+n+'-cases.jsonl.gz',z.gzipSync(f.readFileSync('datasets/golden/'+n+'-cases.v3.jsonl'),{level:9}))"
```
