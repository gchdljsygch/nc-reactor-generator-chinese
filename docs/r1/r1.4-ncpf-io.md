## 3. 移植了什么

### 3.1 读取层（`project.ts`）

等价 Java `NCPFReader` → `NCPFFileReader.read` + `JSONNCPFReader`：

- `JSONNCPFReader.read` 要求根对象有整数 `version`，否则「不是 NCPF」——TS 抛 `NcpfFormatError`（Java 返回 `null` 让位给下一个 reader；R1.4 只有 JSON 一种 NCPF 格式，所以直接报错并在文档里说明）。
- `readNcpfProject(path | string)`：以 `{` 开头的串当 JSON 文本，否则当文件路径；另有显式的 `parseNcpfProject` / `readNcpfPath`。非 JSON（例如 `datasets/fixtures/usfr-legacy-ncpf.ncpf`）会给出「LegacyNCPF 属 R2」的明确错误。
- **全保真**：文档同时持有（a）解析后的 JSON 树 `raw` 与（b）`@ncplanner/ncpf` 的 `buildProject` 视图 `ncpf`，再加配置/设计视图。未知模块、未知字段、未知设计类型原样保留，是 Java 对象模型往返的**超集**（Java 会丢掉没有对应 `NCPFModule` 类的字段）。
- 设计引用在读取时即解析为**元素对象**（`designs.ts`），`grid.blocks` / `grid.recipes` / `scalarReferences` 三部分；`-1` / 越界 → `null`，越界（非负）会在 `document.issues` 里留下诊断。Java 在这里会抛 `IndexOutOfBoundsException`（`NCPFObject.getDefined3DArray` → `indicies.get(idx)`），TS 选择容错 + 报告。

### 3.2 元素身份的精确移植（`javaModel.ts`）

R0 指纹定义为 `definition.type + "|" + definition.toString() + "|" + getDisplayName()`，所以它是 Java `toString()`/`getName()` 的**逐字节**函数。因此本包自带一套精确移植，而**不复用** `@ncplanner/ncpf` 的 `definitionIdentity` / `definitionName`：

| 差异点 | Java | `@ncplanner/ncpf` | 本包（`javaModel.ts`） |
|---|---|---|---|
| `legacy_recipe` 的 inputs/outputs | `HashSet` → **排序 + 去重**后拼接 | 保持 JSON 顺序 | 排序 + 字符串去重（`uniqueSorted`） |
| 未注册的 `type` | 落到 `UnknownNCPFElement`：`type = null`、`getName() = "null"` | 回显原始 type 串 | `null` + `"null"` |
| `legacy_block`/`item` 的 `toString()` | 追加 `:metadata`、blockstate、nbt | 同 | 同（含 `NCPFBlockElement`/`NCPFItemElement` 的无 metadata 变体） |
| `getDisplayName()` 的回退 | `definition.getName()`（**不是** `toString()`） | 用 `definitionName` | 用 `javaDefinitionName` |

> **量化**：语料里共 23 个 `legacy_recipe` 元素，其 `inputs`/`outputs` 的 JSON 顺序**恰好都已排序且无重复**，所以上表第一行是**潜在**分歧、当前语料上不可观测。R2 做 addons / 真实历史文件时必须继续保持两套视图分离（这也是本包不把精确移植塞进 `ncpf` 的原因：`ncpf` 是「逻辑视图」，`formats` 是「冻结格式视图」，见 §8）。
>
> `javaElementDisplayName` 的回退从 `toString()` 改成 `getName()` 是修过一个真实 bug：`addons/*.ncpf.json` 的 27 个文件因此从「行数对、哈希不对」变为一致（显示名回退对 `legacy_block` 会丢掉 metadata/blockstate）。

### 3.3 配置规格（`configSpecs.ts`）

NCPF 的线格式**不描述**「`configuration.<id>` 里哪些键是元素表」，也不知道哪个元素携带方块配方——这些知识在 Java 的 120 个手写类里。R1.4 把它变成数据：

| 配置 id | `getName()` | 元素表 | 配方门模块（`blockRecipeGate`） | 端口模块 |
|---|---|---|---|---|
| `nuclearcraft:overhaul_sfr` | Overhaul SFR Configuration | blocks, coolant_recipes | `…:fuel_cell` | `…:recipe_ports` |
| `nuclearcraft:underhaul_sfr` | Underhaul SFR Configuration | blocks, fuels | `…:active_cooler` | — |
| `nuclearcraft:overhaul_msr` | Overhaul MSR Configuration | blocks | `…:fuel_vessel` | `…:recipe_ports` |
| `nuclearcraft:overhaul_turbine` | Overhaul Turbine Configuration | blocks, recipes | — | — |
| `nuclearcraft:overhaul_distiller` | Overhaul Distiller Configuration | blocks, recipes | — | — |
| `plannerator:fusion_test` | **Fusion Test Configuration** | blocks, coolant_recipes, recipes | `plannerator:fusion_test:breeding_blanket` | — |
| 其它（未注册） | **Unknown Configuration** | — | — | — |

每一行都在代码注释里给了 Java 出处（例如 `ncpf/configuration/NCPFOverhaulSFRConfiguration.java:14`、`planner/ncpf/configuration/OverhaulFusionConfiguration.java:77`）。要点：

1. **`getName()` 不是 JSON 键**（fusion 的键是 `plannerator:fusion_test`，名字是 `Fusion Test Configuration`；未注册配置一律 `Unknown Configuration`），指纹写的是 `getName()`。
2. **元素表 = 声明的 plannerator 字段**，顺序即声明顺序（`OverhaulSFRConfiguration:20-21` 等）。
3. **配方门**：`BlockRecipesElement.getBlockRecipes()` 返回该元素类的**第一个**配方字段（该 list 对象永不为 `null`），而该字段只在对应模块存在时才被填充（`DefinedPlanneratorRecipe.convertFromObject`）。所以 MSR 的 96 个「单配方」方块**不进** `getAllElementsISaidAllElements()`，只有 3 个 `fuel_vessel` 的 27 条燃料配方进；SFR 同理只有 `fuel_cell` 的 81 条。
4. **端口共享父元素配方**：`RecipePortsModule.setLocalReferences` 把 `input.block.parent = output.block.parent = <持有该模块的方块>`，随后 `DefinedPlanneratorRecipe.setReferences` 把父元素的配方 list **按引用**拷给端口——这就是为什么 `fission_cell_port[active=false/true]` 在指纹里也带着 81 条燃料配方。

### 3.4 指纹（`fingerprint.ts`）

逐行移植 `RoundTrip.java:411-447`（`signature()`）：配置名 + 元素身份 + 显示名，排序后 SHA-256 取前 12 字节 + `#<行数>`。三个容易做错的点，代码里都写了 Java 出处：

1. **addon 的配置不写 `cfg|` 行**：Java 只写 `addon|<name>` 与 `ael|<addon>|<cfgName>|…`。这就是 `alloy_heat_sinks.ncpf.json` 的 `988 = 983 元素 + 4 主配置 + 1 addon`。
2. **`getAllElementsISaidAllElements()` 不是「声明的元素表」**：它还会追加每个元素的第一个方块配方表，最后追加 `plannerator:global_elements`（仅当该模块存在且非空——`GlobalElementsModule.exists()`）。
3. **端口按父元素共享配方表**（见 §3.3 第 4 点）。

### 3.5 设计引用（`designs.ts`，R1.4d）

线上格式里设计用**整数索引**引用元素（`-1` = 无）。Java 用 `NCPFObject.indexof` → `NCPFElementDefinition.matches` 解析，而这正是 R0 发现 9 证明**坏掉**的路径（`NCPFSettingsElement.matches()` 对 `legacy_recipe` 不自反）。TS：

- 读取时把索引解析成**元素对象**（身份即 `javaDefinitionToString`）；
- 写入时用**身份 → 索引**（`identityIndex`，首次匹配优先）重新计算；`null` → `-1`；
- `block_recipes` 是**压缩 3D 网格**（只含带 `ncpf:block_recipes` 模块的格子，按 x 片/y 行/z 格的序号索引），`resolveRecipeGrid` / `emitRecipeGrid` 与 `NCPFObject.getRecipe3DArray` / `setRecipe3DArray` 一一对应；
- 只有线格式本来就有 `block_recipes` 键的设计才会写回它（turbine/distiller 设计只写单个 `recipe` 索引，Java 也不写 `block_recipes`）。

**R1.4d 的正向证据**（`r1.4d-identity.test.ts`）：把 `sfr-ncpf-save` 的冷却配方引用按身份赋成 `coolant_recipes[0]`（一个 `legacy_recipe`，输入/输出非空，正是 Java `Set` 分支命中的形状）后保存，写出的是 `"coolant_recipe": 0`，而不是 Java 会写出的 `-1`。

## 4. 两种 writer 语义并排

| | `writeNcpfSave` | `writeNcpfExport` |
|---|---|---|
| Java 对应 | `NCPFFileWriter`（`Core.java:611`） | `NCPFWriter`（`FileWriter.NCPF`，`MenuMain:316-320`） |
| 用途 | **用户保存工程** | **导出单个多方块** |
| 前置处理 | 无 | `project.copyTo()` → `Project.makePartial()`（`Project.java:73-84`） |
| 配置裁剪 | 不裁剪 | 只保留 `design.definition.type` 命中的配置；`addons.clear()` |
| 元素裁剪 | 不裁剪 | `NCPFConfiguration.makePartial` → 每个声明元素表按 `Design.getElements()` 过滤；存活方块再过滤其 `ncpf:block_recipes` 配方（`ElementListPlanneratorField.makePartial`、`DefinedNCPFObject.makePartial`） |
| 模块裁剪 | 不裁剪 | `trimPlanneratorModules`（`NCPFWriter.java:40-70`）：对树中**每个**含 `"modules"` 的对象，删除所有**不以 `ncpf:` 开头**的键；删空后整个 `"modules"` 键移除 |
| 保留 | 全部原样 | **仅 `ncpf:*`**（语料里只有 `ncpf:block_recipes`，含空 `recipes` 数组也保留——`trimModules` 只看键前缀） |
| 裁掉 | — | `plannerator:display_name` / `texture` / `legacy_names` / `tags` / `global_elements` / `configuration_metadata` / `metadata` / `fork…`、`plannerator:fusion_test:*`、`plannerator:generator_settings`，以及全部 `nuclearcraft:*`（元素与游戏玩法数据） |
| 设计引用 | 按身份重算索引 | 同上，但索引针对**裁剪后**的元素表 |
| 与输入的关系 | 未修改的工程**逐字节**等价（TS 是 Java 的严格超集） | 结构保留、装饰被裁；`usfr` 用例与 Java 输出逐字节一致 |

**语料实测（38 个文件）**：共 76 个不同模块键 —— `plannerator:*` 出现 **44,836** 次（23 个不同键）、`nuclearcraft:*` **26,218** 次、`ncpf:*` **3,716** 次（只有 `ncpf:block_recipes`）。即导出语义会删掉 71,054 处模块键、保留 3,716 处。

> ⚠️ 铁律 5（`docs/rewrite-plan-r1-r5.md` §11.2）：两种语义不得混用。TS 侧是两个独立函数，签名不同（导出多一个 `designIds`），且测试分别断言。

## 6. 关于 `npx tsc --noEmit` 的说明

本会话期间 `packages/kernel/src/msr/**` 被**另一个并发写入者**（同一工作区）持续修改，因此中途的两次 `npx tsc --noEmit` 曾报出只属于 `packages/kernel` 的错误（先是 `msr/config.ts(245)` 的 `coilRuleModule`，后是 `msr/reactor.ts` 的 `blocksLOS` / `createsCluster` / `isCasing` / `amount` 只读）。这两次运行里 **`packages/formats` 的错误数都是 0**，我也未改动 `packages/kernel`；最终一次运行（§5.4）全仓库 exit 0。若后续 CI 再看到 `packages/kernel` 的错误，请按 §11.2 的约定找 kernel 的负责人，不要通过改 `formats` 绕过。

## 7. 未达成 / 未往返的项

1. **`datasets/fixtures/sfr-ncpf-save.ncpf.json` 里的 `coolant_recipe: -1` 无法恢复**。
   这不是 TS 的失败：那个 `-1` 是 **Java 写文件时**就写坏的（R0 发现 9；`docs/r0/findings.md` §8.4 的传导路径）。文件里没有任何信息能指出设计原本引用哪个冷却配方，所以 TS 读取时得到 `null`、保存时**保持 `-1` 不变**（`r1.4d-identity.test.ts` 断言了这一点）。
   - TS 读这个 fixture **不抛异常**（Java 会 NPE）；
   - TS **不会**再产生这种值：按身份赋引用后写出的是 `0`（同测试）；
   - 冻结 Java 版读 TS 写出的该文件，错误与读**原始** fixture 完全相同（都是 `coolantRecipe is null` 的 NPE），说明 TS 既没有加剧也没有掩盖问题。
2. **导出的 `addon` 元素没有合并**。Java 的导出路径作用在 `conglomeration`（主配置 + 各 addon 经 `conglomerate()` 合并的结果，`Project.postConvertFromObject` 调用了它），所以 addon 贡献的元素会出现在 Java 的导出里。R1.4 只复刻了「`addons.clear()`」这一半，**没有**实现 `conglomerate()` 的元素/模块合并（它带类型特化语义，例如 `NCPFRecipePortsModule.conglomerate` 直接抛异常、`GlobalElementsModule`/`NCPFBlockRecipesModule` 走 `conglomerateElementList`）。影响面：只有「文件里既有 addon 又有设计」时才会丢元素；随仓库发布的 38 个文件都没有设计，因此基线不受影响。归属：**R2**（`compat-contract.md`；R0 已确认有 addon 的工程是生产数据的一部分）。
3. **读层没有移植 `NCPFFileReader` 的「资源目录回填」**：`NCPFFileReader.java:56-372` 会（a）给缺少 `plannerator:configuration_metadata` 的配置注入 `NuclearCraft (Exported)` + 生成版本号，（b）用文件旁的 `resources/` 目录补 `plannerator:texture`/`display_name`，（c）用内置配置按 `matches()` 回填 `texture`/`display_name`/`legacy_names`。这些是**读入时的副作用**，会改变指纹；但本任务只要求「读文件 + 写文件」的语义等价，且实测语料上该回填**没有产生任何可观测差异**（38/38 指纹一致，元素/显示名计数与 Java 逐文件一致）。归属：R2.1（"NCPF 读取完善：addons、`legacy_names`、全局元素"）——届时若实现，必须注意它会改变 `getDisplayName()` 的结果，需要重跑本基线。

除此之外：**38 个配置全部读入成功、全部保存往返成功**，没有出现「读不进」或「往返指纹不同」的文件；`sfr-ncpf-save` 的 NPE 只发生在**冻结 Java 版**那一侧。

## 8. 与 `packages/ncpf` 的关系（未改动它）

`packages/formats` 复用 `@ncplanner/ncpf` 的 `buildProject`（逻辑视图）与 `makeElement`（元素视图），**没有修改** `packages/ncpf/**`（也不需要新增导出）。两套身份函数并存的理由见 §3.2：

- `ncpf.definitionIdentity` / `definitionName` = **逻辑视图**：用于 kernel、匹配、导入兼容、i18n 身份键（四段式）；
- `formats.javaDefinitionToString` / `javaDefinitionName` / `javaElementDisplayName` = **冻结格式视图**：只用于线格式与 R0 指纹。

两者当前在语料上**不可区分**（23 个 `legacy_recipe` 的顺序恰好已排序、无重复），但一旦 R2 引入更多真实历史文件，差异就可能出现；届时的规则应是「**写文件/算指纹走 formats 视图，做逻辑走 ncpf 视图**」，不要合并。

## 9. 过程记录：交叉验证抓到的一个真实 bug

4 个测试文件在 TS 内部全绿之后，仍做了一次「**让冻结 Java 版读 TS 的导出结果**」的交叉验证，结果 Java 报：

```
java.lang.IndexOutOfBoundsException: Index 64 out of bounds for length 43
```

原因：`writeNcpfExport` 先 `deepCloneJson` 整棵树再裁剪，而设计网格仍指向**原始**的元素对象，于是 `emitRecipeGrid` 用原始（未裁剪，81 条）配方表算出的索引被写进了只含 43 条裁剪后配方的文件。修复方式：导出路径额外传入一个「**按身份查裁剪后元素**」的配方解析器（`write.ts` 的 `recipesByIdentity`），并在 `r1.4c-export.test.ts` 里补上「每个写出的配方索引必须落在写出的配方表内」+「导出物读回后配方身份与导出前一致」两条断言。修复后 Java 的报错回到它**本来的**那个 NPE（即 §7 第 1 项），证明配方网格已经正确。

**教训**：TS 自洽的往返测试无法发现「写出的东西第三方读不了」这类问题；R1.4b 的验收口径写的是「被冻结 Java 版读回」，就必须真的去跑那一步（附录 B）。
