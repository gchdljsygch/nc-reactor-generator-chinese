## 1. 结论

| 项 | 结果 |
|---|---|
| Overhaul MSR | **1,000 / 1,000 通过**（`datasets/golden/msr-cases.jsonl.gz`，0 个 `error` 记录） |
| Overhaul Turbine | **500 / 500 通过**（`datasets/golden/turbine-cases.jsonl.gz`，0 个 `error` 记录） |
| 回归 | Overhaul SFR **5,000 / 5,000**、Underhaul SFR **5,000 / 5,000** 未变化 |

| `node tools/ts/lint.mjs` | 通过（`0 prose literals, 0 baselined`） |
| 重复求值 | 每个数据集的同一记录连续 `recalculate()` 两次，统计量逐字节相同 |

> 「通过」= 黄金记录 `editor` 块中的**每一个**数值字段都匹配：
> 整数字段精确相等，浮点字段相对误差 ≤ 1e-5，`"NaN"` / `"Infinity"` 视为「无参考值」跳过。
> 整数字段实测**全部逐位相同**；浮点字段的实测分布见 §1.3，
> 最大相对偏差 2.40e-7（比 1e-5 门槛小 42 倍）。
> `lite`（应当消失的第二实现）在本堆型上不存在（`"lite": null`），从不作为对拍目标。

### 1.3 逐位一致率（附加测量，不是验收门槛）

验收门槛只有「1e-5 内」这一条。为免夸大，这里给出实测的**按 float32 归一化后**
的逐位一致率（黄金记录里的 `float` 字段以最短十进制形式落盘，`JSON.parse` 得到的是
`double`，所以必须先把两侧都 `Math.fround` 再比，否则会把「十进制表示长度」
误判成差异；`"NaN"` 字段已排除）：

| 数据集 | 可比较字段 | float32 逐位相同 | 1 ULP | > 1 ULP | 最大相对偏差 |
|---|---:|---:|---:|---:|---:|
| Overhaul MSR | 13,876 | 13,758（**99.15%**） | 0 | 118 | 归一化前 1 ULP；归一化后 0 |
| Overhaul Turbine | 7,449 | 6,865（**92.16%**） | 490 | 94 | 2.40e-7（`rotorEfficiency`） |

差异**集中在少数几个浮点字段**，其余字段 100% 逐位相同：

```
MSR      shutdownFactor   : identical 758 / 0 x1ULP / 118 x>1ULP   （见下，归一化造成）
         其余 13 个字段    : 100% float32 逐位相同

Turbine  rotorEfficiency      : identical 335 / 126 x1ULP / 22 x>1ULP
         totalEfficiency       : identical 265 / 182 x1ULP / 36 x>1ULP
         totalFluidEfficiency  : identical 265 / 182 x1ULP / 36 x>1ULP
         （coilEfficiency 的差异全部只是十进制表示长度，float32 下完全一致）
         其余 11 个字段    : 100% float32 逐位相同
```

相对偏差的分位数（不含已归一化的 `shutdownFactor`）：

| 数据集 | 有差异字段数 | 最大 | p50 | p99 | p99.9 |
|---|---:|---:|---:|---:|---:|
| Overhaul MSR | 4,503 | 5.91e-8 | 1.03e-8 | 2.44e-11 | 1.55e-37 |
| Overhaul Turbine | 1,949 | 2.40e-7 | 1.46e-8 | 7.44e-10 | 4.92e-11 |

两个「> 1 ULP」的原因都在这里，没有第三条：

1. **MSR `shutdownFactor` 的 118 例全部是归一化造成的**，不是物理差异。
   冻结引擎在这里给出**负数**，而 §3.1.5 把 `shutdownFactor` 定义在 `[0,1]` 上
   并要求**两侧同时归一化**，于是黄金侧的负值与 TS 侧的负值都被归一到 `0`
   → 判定通过。
   > 负数从哪来：`shutdownFactor = 1 - offOutput/totalTotalOutput`，
   > 当部分停机阶段的产出小于停机阶段的产出时就是负的。冻结引擎照算不误。
   >
   > **裸值也一致**（`statsRaw()` 保留未归一化的值，可直接对拍）：
   > ```
   > msr-000006: golden=-1.0745456 tsRaw=-1.0745456218719482
   >             offOutput=6.541571617126465 totalTotalOutput=3.153254985809326
   > msr-000041: golden=-39.243385 tsRaw=-39.243385314941406
   >             offOutput=1.910035252571106 totalTotalOutput=0.047462090849876404
   > ```
   > 即归一化层没有掩盖任何东西：规范化前两边的差异也只是 1 ULP。
2. **Turbine 的 94 例是 `rotorEfficiency` 链上的浮点噪声**：
   `rotorEfficiency`（`float`）→ `totalEfficiency`（`double`）→
   `totalFluidEfficiency`（`double`，再乘 `power`）逐级放大 1 ULP。
   实测样例（均为交付数据集里的真实记录）：
   ```
   turbine-000000 rotorEfficiency      golden=0.8580458          ts=0.858045756816864    rel=5.03e-8
   turbine-000000 totalEfficiency      golden=0.31213510962496405 ts=0.3121350763952368  rel=1.06e-7
   turbine-000000 totalFluidEfficiency golden=4.994161753999425  ts=4.994161222323789    rel=1.06e-7
   turbine-000007 rotorEfficiency      golden=0.28297058         ts=0.2829706072807312   rel=9.64e-8
   ```
   最大相对偏差 2.40e-7，比 1e-5 门槛小 42 倍。

> 更正记录：`docs/r1/float-fidelity.md` §8 结尾写「实测的浮点差异在修正上述规则后
> **逐位相同**」。这句话对 SFR/USFR 成立，对本轮的 Turbine **不成立**——
> Turbine 的 `totalEfficiency` 在全 500 例上都不是 `Object.is` 逐位相同。
> 原因不是规则没落地，而是 R1.0a 的 `--repeat 10` 只证明了 Java 引擎**自身**可复现，
> 没有证明「TS 的运算顺序 == Java 的运算顺序」在每一个中间量上都成立。
> 本轮没有把这些字段追到逐位相同，因为验收契约（§3.1）本来就是 1e-5。

## 3. 新结构

### 3.1 MSR `VesselGroup`（燃料容器组）

Java 里 `OverhaulMSR` 的物理量**不在方块上**，而在 `VesselGroup` 上：

| 量 | 归属 | 语义 |
|---|---|---|
| `blocks` | 组 | 4-邻接洪水填充的结果，要求 `newBlock.isEqual(start)`（模板定义相等）**且** `newBlock.fuel == start.fuel`（**同一个 `Fuel` 对象**） |
| `criticality` | 组 | `fuelCriticality * getSurfaceFactor()`；`fuelCriticality` 取遍历中**最后一个**非空 `block.fuel` 的 `criticality` |
| `neutronFlux` | 组 | `propogateNeutronFlux` 累加的对象；慢化剂分支是 `int += int`，反射器分支是 `int += float`（截断，走 `intAccumulateFloat`） |
| `moderatorLines` | 组 | 每次成线 +1（含反射器 / 辐照器分支） |
| `positionalEfficiency` | 组 | `float`，逐段 `efficiency/length` 累加，`initVessels` 时**原地**乘 `getBunchingFactor()` |
| `isActive()` | 组 | `neutronFlux >= criticality` |
| `getOpenFaces()` | 组 | 6 个方向中「组内没有邻居」的方向数，只算一次并缓存（`openFaces = -1` 失效） |
| `getBunchingFactor()` | 组 | `6*size()/getOpenFaces()`，Java **整数除法**后拓宽为 `float` |
| `getSurfaceFactor()` | 组 | `getOpenFaces()/6`，整数除法 |
| `getHeatMult()` | 组 | `moderatorLines * getBunchingFactor()`（`int * float`） |
| `getSources()` / `getRequiredSources()` / `isPrimed()` | 组 | 源的个数 / 自持所需源数 = `getSurfaceFactor()` |

**对象身份是有语义的。** 每个 VesselGroup 的 key 是「模板 + `Fuel` 实例」，
所以重建器（`rebuildMsr`）必须让所有记录同一燃料名的方块**共用同一个 `MsrFuel` 对象**
（`fuelCache`）。若按名字每次新建对象，邻接的同类容器就不会归入同一组，
`totalFuelVessels` / `criticality` / `totalHeat` 会整片错位。
金样本生成器（`GoldenGen.fillMSRInterior`）正是这么做的：它从模板的 `fuels` 列表里取
一个对象喂给连续若干个容器。

**生命周期。** `VesselGroup.clearData()` 会清空组内所有方块的 `clearData()`，
并把 `openFaces` 重置为 -1；但 `buildGroups` 里 `for(Block b : allBlocks)b.vesselGroup = null`
是另一条独立的清理路径（`Block.clearData()` **不**清 `vesselGroup`，Java 注释明说
"doesn't even need to be reset"）。两处都照搬。

**三阶段与 `vesselGroupsWereActive`。** shutdown 阶段用 base 阶段**创建出来的组对象**
做 `force` 标记（`vesselGroupsWereActive` 是一个按身份比较的集合），
然后 `clearData()` 会重建 `vesselGroups` 列表——这些是新对象，所以 base 阶段的标记在
shutdown 阶段**不会**命中任何组。这是冻结引擎的既有语义，已照搬，
`docs/r1/r1.5-kernel.md` §4 第 6 条记录过 SFR 上同类的「旧实现语义」。

### 3.2 MSR 加热器（heater）

与 SFR 散热器的三处差别：

1. **配方先行**：`calculateHeater` 在 `block.heaterRecipe == null` 时立即返回 `false`
   （连 `heaterValid` 都不动），SFR 的散热器没有这一步。
2. **规则来源**：Java `AbstractBlock.getRules()` 先看**模板**上的 `BlockRulesModule`，
   都没有才看**配方**上的。MSR 的 `HeaterModule extends BlockRulesModule` 就挂在模板上。
3. **产出栈**：`calcStats` 里对每个「模板有 heater 且配方非空」的方块累加
   `out = c.efficiency * sparsityMult`，并把配方的 outputs 累进 `totalOutput`
   （仅当配方是 `legacy_recipe`；纯 `legacy_fluid` 没有 in/out 栈，Java 有显式守卫）。
   `totalTotalOutput += out` 与配方形态无关。

### 3.3 Turbine 转子几何

| 量 | 定义 | 备注 |
|---|---|---|
| `minBearingDiameter` | `width%2==0 ? 2 : 1` | |
| `maxBearingDiameter` | `width-2` | |
| 轴承候选 | `i` 从 min 到 max **步长 2**，`bearingMin = extW/2 - i/2`，`bearingMax = extW/2 + i/2 - (i%2==0?1:0)` | 整数除法 |
| 轴承校验 | 对每个 `(x,y)` 遍历 `z = 0..extD-1`；`z` 在两端要求 `bearing` 模块，否则要求 `shaft` | 任一不满足就 `break BEARING` 到下一个直径；**校验通过的最后一个**直径胜出 |
| 叶片环 | 内部 `(x,y)` 中「恰好一个轴落在轴承范围内」 | `xBlade == yBlade` 的格子跳过（两个都真 = 轴承，两个都假 = 环外） |
| 每层模板 | 同一 `z` 层所有叶片/定子必须是**同一个模板对象**，否则该层记为 `null`（`badBlade`） | 有一格空气则该层 `bladesComplete[z-1] = false` |
| `rotorValid` | 所有层都非 `null` | `bladeCount` 为非空层数 |
| `idealExpansion[i]` | `coefficient^((i+0.5)/n)` | `double` |
| `actualExpansion[i]` | `expansionSoFar * sqrt(expansion)`，随后 `expansionSoFar *= expansion` | `double`；`expansion` 是 `float` |
| `rotorEfficiency` | `Σ blade.efficiency * min(actual/ideal, ideal/actual)`，再 `/ numberOfBlades` | `float` 逐步收窄 |
| `maxInput` | `bearingDiameter*4*(width/2 - bearingDiameter/2) * fluidPerBlade`，全整数 | |
| 线圈 | `valid` 需要「6 邻中至少一个 valid 的线圈/连接器/轴承」**且**自身规则通过 | 迭代到不动点 |

**`getInputRate()` 恒等于 `maxInput`**（Java 方法体是 `return maxInput;`，
真正的输入路径被注释掉了）。因此 `throughputRatio` 恒为
`min(1, (maxInput+absoluteLeniency)/maxInput) = 1`，
再因 `1 ≥ throughputEfficiencyLeniencyThreshold(0.75)` 使
`throughputEfficiencyMult = 1`。两条分支都照实写了，没有走捷径。

## 4. 字段映射表

### 4.1 MSR 数值字段

`stats.ts` 里 `MSR_INTEGER_FIELDS` 与浮点集合（未列入者即浮点）：

| 字段 | Java 类型 | 出处 | 语义 / 计算式 |
|---|---|---|---|

| `totalCooling` | `int` | `:61` | `Σ 活跃加热器配方的 cooling`（`heater_stats.cooling` 是 `int`） |
| `totalHeat` | `int` | `:62` | `Σ (moderatorLines*heat*bunchingFactor) + Σ(heatPerFlux*flux) + Σ(irradiator.heat*flux)` |
| `netHeat` | `int` | `:63` | `Σ cluster.netHeat`，`cluster.netHeat = totalHeat - totalCooling` |
| `totalIrradiation` | `int` | `:66` | `Σ 活跃辐照器的 neutronFlux` |
| `functionalBlocks` | `int` | `:67` | 变体 `isFunctional()` 的方块数 |
| `numControllers` | `int` | `:78` | 壳层扫描中 `isController()` 的个数 |
| `missingCasings` | `int` | `:79` | 壳层扫描中缺失/非壳层的格数 |
| `totalEfficiency` | `float` | `:64` | `Σ(cluster.efficiency*fuelVessels) / totalFuelVessels * sparsityMult` |
| `totalHeatMult` | `float` | `:65` | `Σ(cluster.heatMult*fuelVessels) / totalFuelVessels` |
| `sparsityMult` | `float` | `:68` | 同 SFR：阈值比较用 **float 除法**，否则 `(float)(m+(1-m)*sin(π·fb/(2·V·t)))` |
| `totalTotalOutput` | `float` | `:70` | `Σ over 加热器方块 (c.efficiency*sparsityMult)` |
| `shutdownFactor` | `float` | `:71` | `1 - offOutput/totalTotalOutput`，比较时按 §3.1.5 归一到 `[0,1]` |
| `offOutput` | `float` | `:115` | shutdown 阶段的 `totalTotalOutput`（case 21 写入）。`clearData` **不**重置它，因此 partial shutdown 阶段仍能读到；`totalTotalOutput` 本身每阶段都被清零 |
| `totalOutput`（`ArrayList<NCPFElementStack>`） | 非数值 | `:69` | 逐产出栈累加；不进入统计比较，仅为完整性保留 |

> 数据集实测：MSR 的 14 个字段在 1,000 例上全部匹配。
> `totalIrradiation` 恒为 0——随附配置里 3 条辐照器配方的 `heat` 与 `efficiency` 分别是
> `0`（Thorium / TBP，`efficiency=0`）与 `0/0.5`（Bismuth），且该堆型的
> `totalIrradiation` 从不参与任何输出，所以恒为 0 不是「漏算」。

| `rotorEfficiency` | `float` | `:46` | 见 §3.3 |
| `coilEfficiency` | `float`（private） | `:51` | `(inputEff+outputEff)/2`，两侧各自 `/ max(coils, bearingDiameter²/2)`（整数除法） |
| `throughputEfficiency` | `double`（private） | `:49` | `(1 + powerBonus*(lengthBonus*areaBonus)^(2/3)) * throughputEfficiencyMult` |
| `idealityMultiplier` | `double`（private） | `:50` | `min(expSoFar, coefficient)/max(expSoFar, coefficient)` |
| `totalEfficiency` | `double`（private） | `:52` | `coilEfficiency*rotorEfficiency*throughputEfficiency*idealityMultiplier` |
| `totalFluidEfficiency` | `double`（private） | `:53` | `totalEfficiency * recipe.stats.power`（`power` 是 `double`，不收窄） |

> 数据集实测：Turbine 的 15 个字段在 500 例上全部匹配。
> `recipe.stats.{power,coefficient}` 是**双精度**且从不收窄（`docs/r1/float-fidelity.md` §6 的镜像情形），
> 因此 `throughputEfficiency` / `idealityMultiplier` / `totalEfficiency` /
> `totalFluidEfficiency` 全程按 `double` 计算，只在 `coilEfficiency`/`rotorEfficiency`
> 两处按 Java 的 `float` 收窄。
> `totalOutput` / `safeOutput` / `unsafeOutput` 是 `long`，用 `Math.trunc` 向零截断
> 并对 `long` 边界饱和（`javaLong`）。

### 4.4 配方命名与重建

- 数据集 v3 用 `definition.toString()`（单射）给模板和配方命名；
  `rebuildMsr` / `rebuildTurbine` 先按**身份**查表，查不到再按（有损的）`definition.name`
  回退并把歧义记进 `ambiguous`，与 `rebuildSfr` 完全同形。
- 配方串格式 `<字段名>=<definition.toString()>`。MSR 的三个字段：
  `fuel`（容器/容器端口）、`heaterRecipe`（加热器）、`irradiatorRecipe`（辐照器）。
  Turbine 不存在方块级配方（`Block.getRecipes()` 返回空表），因此 `recipeNames` 全为空。
- **配方端口（`recipe_ports`）**：随附配置里 34 个模板带 `recipe_ports`
  （16 个 `salt_fission_heater` + 16 个 `salt_fission_heater2` + `salt_fission_vessel` +
  `fission_irradiator`），对应 68 个端口模板（每个 owner 有 input/output 两个，
  heater2 系列还各分 active=false/true 两种）。已逐条核对：
  **68 个端口方块自己的 `ncpf:block_recipes` 列表与父方块的列表长度与内容完全一致**
  （`ownRecipes.length == parentRecipes.length`，且逐项同名）。因此 `assignMsrRecipe`
  一律读「本模板自己的配方列表」，这条路径对端口与非端口都成立。
- 无法解析的配方名**抛错**（不是静默忽略）：漏一条加热器配方就会少算冷却。

## 5. 浮点保真的落地（对照 `docs/r1/float-fidelity.md`）

| 规则 | MSR / Turbine 上的落点 |
|---|---|
| 1. 读入即 `fround` | `msr/config.ts`：`fuel_stats.{efficiency,time}`、`heater_stats.cooling`(int)、`irradiator_stats.*`、`moderator.efficiency`、`reflector.*`、`neutron_shield.efficiency`、`neutron_source.efficiency`、settings 的两个 `float`。`turbine/config.ts`：`blade.*`、`stator.expansion`、`coil.efficiency`、settings 的四个 `float`；`recipe_stats.*` 是 `double` **不收窄** |
| 2. 逐步 `fround` | `initVessels` 的三次 `fmul`（`a*b*c*d` 在 Java 里舍入三次）；`cluster.efficiency += b.efficiency`；`rotorEfficiency += (float)(blade.efficiency*ratio)` 写成 `d2f(rotorEfficiency + d2f(bladeEfficiency*d2f(ratio)))` |
| 3. `int += float` | MSR 只有反射器分支：`group.neutronFlux += flux*2*reflectivity`（`reflectivity` 是 `float`，走 `intAccumulateFloat`）。Turbine 无此形态 |
| 4. 求和顺序 | 方块扫描 x→y→z（`CuboidGrid.blocks`）、方向 `PX,PY,PZ,NX,NY,NZ`、簇/组的发现顺序按 `allBlocks`、组内方块按分层 BFS 层序展平 |
| 5. Java 的 `double` 表达式最后一次 cast | `sparsityMult`（同 SFR，公式逐字相同）；`criticalityModifier = (float)(1/(1+exp(2*(flux-2*crit))))` |
| 6. `double` 只承载 `float` 商 | Turbine 的 `throughputEfficiency` / `idealityMultiplier` / `totalEfficiency` / `totalFluidEfficiency` 是原生 `double`，全程用 `number`；`totalOutput` 一族是 `long`，向零截断 |

**整数除法**（易错点，已逐处复刻）：
`getSurfaceFactor()`、`getBunchingFactor()` 的分子、
`bearingMin/bearingMax`、`numBlades`/`bladeArea` 的 `width/2 - bearingDiameter/2`、
`Math.max(inputCoils, bearings/2)`、`(minWidth-1)*2`。

## 6. 调试方法（沿用 R1.5）

1. **先对拍自造语料**。本轮在验收数据集交付前，先用冻结引擎自造了两批临时语料
   （写入系统临时目录，不落在仓库里）：

   用一个临时 vitest 探针复用与正式测试相同的重建 + `compareStats` 路径逐条对比，
   **1,000/1,000 全字段通过**后再切到正式数据集。
2. **逐方块对拍**：`packages/kernel/test/block-dump.test.ts` 已参数化
   （`NCPL_DUMP_TYPE` = `sfr` | `msr` | `turbine`，缺省由 `NCPL_DUMP_DATASET` 推断），
   MSR 分支额外打印 `vesselGroup` 的 `size/flux/criticality/openFaces/surfaceFactor/
   moderatorLines/positionalEfficiency/bunchingFactor/heatMult/primed`
   ——因为这些量在 MSR 上属于组而不属于方块，只打印方块字段是看不出问题的。
   ```powershell
   NCPL_DUMP_ID=msr-000000 NCPL_DUMP_DATASET=datasets/golden/msr-cases.jsonl.gz `
     npx vitest run packages/kernel/test/block-dump.test.ts

## 7. 与冻结引擎的（有意）差异

1. **`totalIrradiation` 不进入任何输出**：Java 累加它却不使用。已照搬，
   所以它在 MSR 上是恒 0 的观测值而不是「被漏掉的输出」。
2. **`totalOutput`（产出栈列表）不做比较**：它不是数值字段，Java 的反射统计也拿不到它。
   实现里保留（`MsrElementStack`），并在 `stats()` 之外暴露，仅供后续 R3/R4 使用。
3. **Turbine 的 `inputs` / `getInputRate()`**：Java 里 `inputs` 是空列表、
   `getInputRate()` 直接 `return maxInput`。当前实现保持同一行为，不引入新语义。
4. **纯记账字段不导出**：`calcStep` / `calcSubstep` / `steps` / `stps` /
   `somethingChanged` / `lastChangeTime` / `x` / `y` / `z`。
   `docs/rewrite-plan-r1-r5.md` §3.1 的 `NON_RESULT_FIELDS` 已把它们排除在黄金值之外
   （`GoldenGen` 的反射遍历会跳过它们）。`bladeCount` **在**导出集合里
   （`GoldenGen` 把 private 的 `int` 也抓进黄金值），见 §4.2。

**没有未解释的失败。** 两个数据集上的失败数都是 0。
