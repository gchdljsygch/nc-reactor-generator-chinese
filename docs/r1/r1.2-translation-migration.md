## 2. 完整性核对：1,185 条一条不落

每条遗留翻译对**恰好**落入下面五类之一，计数恒等式成立：

```
遗留翻译对            1185
  = 数据名对          31
  + UI 文案对         1154

UI 文案对             1154
  = 唯一 key          1101   （大小写不敏感去重，与 R0.5 的 PowerShell 哈希表口径一致）
  + 重复出现          53

唯一 key              1101
  = 自动分类          283
  + 需人工判断        818

数据名对              31
  → 四段式身份键      26   （多条遗留对命中同一元素，合并）
```

恒等式校验：31 + 1154 = 1185 ✓；1101 + 53 = 1154 ✓；283 + 818 = 1101 ✓

脚本在写入产物前会断言这三条恒等式（以及「草稿 key 大小写不敏感折叠后无冲突」），
任一条不成立即抛错并中止，不会产出数字对不上的报告。

另有 0 条唯一 key 在草稿中的译文与遗留对首次出现的译文不一致（R0.5 用「先出现者胜」，理论上应为 0）。

规则按**顺序**匹配，先命中者生效。设计原则：只有在证据充分（句子结构完整）时才自动重新 key 化。

处理方式建议：

1. `fragment-*` —— 这些条目从来不是一条消息，而是旧表用来替换句子成分的词。它们**不应**成为独立 key：

## 5. 已知局限

1. **key 是临时产物**：前缀是启发式判定，后缀由英文机械生成。R3.8 抽取代码字符串时应同时冻结语义 key，
   本报告的映射表就是那次评审的输入。
2. **没有复数信息**：旧表用子串替换，无法表达单复数。`en_US` 种子包因此只有单形消息；
   复数形态（`{one}/{other}` 对象）必须在 R3.8 人工编写（机制见 `docs/r1/r1.2-i18n.md`）。
3. **没有占位符信息**：旧表把参数拼接在句子中间，本脚本无法还原参数位置，所以带冒号/空白的条目全部进人工队列，
   而不是猜一个 `{0}` 位置。
4. **大小写口径**：去重沿用 R0.5 的 PowerShell 大小写不敏感行为（否则无法复现 1,101 这个数字）；
   产物本身是大小写敏感的，重复项已在上文列出。
5. **元素覆盖率仍很低**：26 / 948（2.7%）。未被覆盖的元素按设计整条回退到英文 canonical 名，
   这 922 个元素就是中文包的后续工作量（`packages/i18n/test/dataNames.test.ts` 会断言该数字）。
